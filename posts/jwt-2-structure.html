1. JWT의 정의와 표준

1.1 JWT(JSON Web Token)란?

공식 정의

JSON 형식으로 인코딩된, 암호학적으로 서명된 클레임(Claims)을 담은 컴팩트하고 URL-safe한 토큰

JWT의 탄생 배경

문제: API 인증을 위한 표준이 없었음
├── 각 회사마다 다른 토큰 형식
├── 상호 운용성 부족
└── 보안 취약점

해결: JWT 표준 등장 (RFC 7519)
├── 명확한 구조 정의
├── 검증 방식 표준화
└── 업계 전반에서 채택

1.2 RFC 7519 표준

RFC란?

Request for Comments: 인터넷 기술 표준을 정의하는 문서

JWT 관련 RFC

RFC제목내용
RFC 7519JSON Web Token (JWT)JWT의 기본 구조와 처리 방법
RFC 7515JSON Web Signature (JWS)JWT 서명 방식
RFC 7516JSON Web Encryption (JWE)JWT 암호화 방식
RFC 7518JSON Web Algorithms (JWA)JWT에 사용되는 알고리즘

1.3 토큰 기반 인증에서 JWT의 위치

인증 토큰의 종류

인증 토큰
├── Opaque Token (불투명 토큰)
│   └── 랜덤 문자열 (예: "abc123xyz789")
│       └── 서버에서 조회해야만 의미 파악 가능
│
└── JWT (Self-contained 토큰)
    └── 구조화된 데이터 (JSON)
        └── 토큰 자체에 정보 포함

비교 예시

Opaque Token:
"7a9f2c8e1b4d3a5f6e8c9d0a2b4c6e8f"
└─> 서버: "이게 누구의 토큰이지?" → DB 조회 필요

JWT:
"eyJhbGci...eyJ1c2Vy...SflKxw"
└─> 서버: 토큰을 열어보면 → 사용자 정보 바로 확인
    { "user_id": 1, "email": "user@example.com" }

1.4 JWT 활용 사례

1. API 인증

2. Single Sign-On (SSO)

사용자 → [인증 서버] 로그인
           ↓
        JWT 발급
           ↓
    ┌──────┴──────┐
    ↓             ↓
[서비스A]     [서비스B]

한 번 로그인으로 여러 서비스 사용

3. 정보 교환 (Information Exchange)

// 서비스 간 안전한 정보 전달
{
  "order_id": 12345,
  "amount": 50000,
  "timestamp": 1670000000,
  "signature": "..."  // 위변조 방지
}

2. JWT의 구조 이해

2.1 JWT의 3가지 구성 요소

JWT 형태

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyX2lkIjoxLCJlbWFpbCI6InVzZXJAZXhhbXBsZS5jb20iLCJleHAiOjE2NzAwMDAwMDB9.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

구조:
┌──────────── Header ────────────┐ ┌───────────── Payload ─────────────┐ 
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 . eyJ1c2VyX2lkIjoxLCJlbWFpbCI6InVzZXJA... . 
┌──── Signature ────┐
SflKxwRJSMeKKF2QT4f...

3가지 부분

  1. Header (헤더): 토큰 메타데이터
  2. Payload (페이로드): 실제 데이터 (Claims)
  3. Signature (서명): 무결성 검증

2.2 Header (헤더): 토큰 타입과 서명 알고리즘

Header 구조

{
  "alg": "HS256",
  "typ": "JWT"
}

필드 설명

필드설명예시 값
alg서명 알고리즘 (Algorithm)HS256, RS256, ES256
typ토큰 타입 (Type)JWT

주요 서명 알고리즘

알고리즘방식설명사용 사례
HS256대칭키 (HMAC)같은 키로 서명 & 검증단일 서버, 간단한 API
RS256비대칭키 (RSA)개인키로 서명, 공개키로 검증마이크로서비스, SSO
ES256비대칭키 (ECDSA)RSA보다 빠르고 키가 작음모바일, IoT

Base64URL 인코딩

원본 JSON:
{"alg":"HS256","typ":"JWT"}

Base64URL 인코딩 후:
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9

2.3 Payload (페이로드): 클레임(Claims) 정보

Payload 구조 예시

{
  "sub": "user@example.com",
  "user_id": 1,
  "name": "홍길동",
  "role": "USER",
  "iat": 1669996400,
  "exp": 1670000000
}

클레임(Claim)이란?

Key-Value 쌍으로 이루어진 정보 조각

등록된 클레임 (Registered Claims)

JWT 표준에서 정의한 예약된 클레임

클레임전체 이름설명예시
issIssuer토큰 발급자"<https://auth.example.com>"
subSubject토큰 주체 (사용자 식별자)"user@example.com"
audAudience토큰 대상 (의도된 수신자)"<https://api.example.com>"
expExpiration Time만료 시간 (Unix timestamp)1670000000
nbfNot Before유효 시작 시간1669996400
iatIssued At발급 시간1669996400
jtiJWT ID토큰 고유 식별자"abc123"

등록된 클레임 예시

// JWT 생성 시
String jwt = Jwts.builder()
    .setIssuer("<https://auth.example.com>")        // iss
    .setSubject("user@example.com")                // sub
    .setAudience("<https://api.example.com>")        // aud
    .setIssuedAt(new Date())                       // iat
    .setExpiration(new Date(System.currentTimeMillis() + 3600000))  // exp
    .setNotBefore(new Date())                      // nbf
    .setId(UUID.randomUUID().toString())           // jti
    .signWith(SignatureAlgorithm.HS256, secretKey)
    .compact();

exp (만료 시간) 동작

현재 시간: 2024-01-01 10:00:00 (1704088800)
exp: 2024-01-01 11:00:00 (1704092400)

10:30 → 토큰 유효 ✅
11:00 → 토큰 만료 ❌
11:30 → 토큰 만료 ❌

서버는 자동으로 exp를 확인하고 만료된 토큰 거부

공개 클레임 (Public Claims)

IANA JWT Registry에 등록하거나, 충돌 방지를 위해 URL 형식 사용

{
  "<https://example.com/jwt_claims/is_admin>": true,
  "<https://example.com/jwt_claims/department>": "Engineering"
}

실무에서는 잘 사용하지 않음.

비공개 클레임 (Private Claims)

개발자가 자유롭게 정의하는 커스텀 클레임

{
  "user_id": 1,
  "email": "user@example.com",
  "name": "홍길동",
  "role": "USER",
  "permissions": ["read", "write"]
}

Java 코드 예시

String jwt = Jwts.builder()
    // 등록된 클레임
    .setSubject("user@example.com")
    .setIssuedAt(new Date())
    .setExpiration(new Date(System.currentTimeMillis() + 3600000))

    // 비공개 클레임 (커스텀)
    .claim("user_id", 1)
    .claim("name", "홍길동")
    .claim("role", "USER")
    .claim("permissions", List.of("read", "write"))

    .signWith(SignatureAlgorithm.HS256, secretKey)
    .compact();

// 클레임 읽기
Claims claims = Jwts.parser()
    .setSigningKey(secretKey)
    .parseClaimsJws(jwt)
    .getBody();

String email = claims.getSubject();
Integer userId = claims.get("user_id", Integer.class);
String name = claims.get("name", String.class);
String role = claims.get("role", String.class);
List<String> permissions = claims.get("permissions", List.class);

주의사항: 민감한 정보 포함하지 않기

// ❌ 절대 안 됨!
{
  "password": "secret123",
  "credit_card": "1234-5678-9012-3456",
  "ssn": "123-45-6789"
}

// ✅ 적절한 정보
{
  "user_id": 1,
  "email": "user@example.com",
  "role": "USER"
}

이유: JWT는 인코딩되었을 뿐 암호화되지 않음!

JWT Payload:
eyJ1c2VyX2lkIjoxLCJlbWFpbCI6InVzZXJAZXhhbXBsZS5jb20ifQ

Base64URL 디코딩하면:
{"user_id":1,"email":"user@example.com"}

→ 누구나 볼 수 있음!

2.4 Signature (서명): 토큰 검증을 위한 서명

서명의 목적

  1. 무결성 검증: 토큰이 변조되지 않았는지 확인
  2. 발급자 검증: 신뢰할 수 있는 서버에서 발급했는지 확인

서명 생성 과정

1. Header와 Payload를 Base64URL 인코딩
   header = base64UrlEncode({"alg":"HS256","typ":"JWT"})
   payload = base64UrlEncode({"user_id":1,"email":"user@example.com"})

2. 점(.)으로 연결
   data = header + "." + payload

3. 지정된 알고리즘으로 서명
   signature = HMAC-SHA256(data, secret_key)

4. 최종 JWT
   jwt = header + "." + payload + "." + signature

시각화

┌─────────────────────────────────────────────────────────────┐
│                         JWT 생성                              │
└─────────────────────────────────────────────────────────────┘

Header JSON                    Payload JSON
{"alg":"HS256","typ":"JWT"}    {"user_id":1,"email":"user@example.com"}
      ↓                               ↓
Base64URL 인코딩              Base64URL 인코딩
      ↓                               ↓
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyX2lkIjoxLCJlbWFpbCI6InVzZXJAZXhhbXBsZS5jb20ifQ
      ↓                               ↓
      └───────────────┬───────────────┘
                      ↓
              HMAC-SHA256(위 문자열, secret_key)
                      ↓
              SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
                      ↓
┌─────────────────────────────────────────────────────────────────────┐
│ eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.                                │
│ eyJ1c2VyX2lkIjoxLCJlbWFpbCI6InVzZXJAZXhhbXBsZS5jb20ifQ.              │
│ SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c                         │
└─────────────────────────────────────────────────────────────────────┘
                        완성된 JWT

검증 과정

1. JWT 수신
   eyJhbGciOi...

2. Header, Payload, Signature 분리
   parts = jwt.split(".")
   header = parts[0]
   payload = parts[1]
   signature = parts[2]

3. Header와 Payload로 서명 재생성
   expectedSignature = HMAC-SHA256(header + "." + payload, secret_key)

4. 서명 비교
   if (signature == expectedSignature) {
     ✅ 유효한 토큰
   } else {
     ❌ 위변조된 토큰
   }

위변조 시나리오

공격자가 Payload 변조 시도:
원본: {"user_id":1,"role":"USER"}
변조: {"user_id":1,"role":"ADMIN"}

1. 변조된 Payload로 JWT 생성
2. 하지만 secret_key를 모르므로 올바른 서명 생성 불가
3. 서버에서 서명 검증 실패
4. 토큰 거부 ✅

3. JWT 인코딩과 디코딩

3.1 Base64URL 인코딩의 이해

Base64 vs Base64URL

Base64:
├── 64개 문자 사용: A-Z, a-z, 0-9, +, /
├── 패딩: = 문자 사용
└── 문제: URL에서 +, /, = 문자가 특수 의미를 가짐

Base64URL:
├── URL-safe: +를 -, /를 _, =는 제거
├── URL의 쿼리 파라미터나 헤더에 안전하게 사용 가능
└── JWT에서 표준으로 사용

인코딩 예시

원본 JSON:
{"user_id":1,"email":"user@example.com"}

Base64 인코딩:
eyJ1c2VyX2lkIjoxLCJlbWFpbCI6InVzZXJAZXhhbXBsZS5jb20ifQ==

Base64URL 인코딩 (JWT에서 사용):
eyJ1c2VyX2lkIjoxLCJlbWFpbCI6InVzZXJAZXhhbXBsZS5jb20ifQ
(마지막 == 제거)

URL에서 사용 예시

일반 Base64 (문제 발생):
<https://api.example.com/verify?token=eyJ...fQ==>
                                        ↑
                                      URL에서 문제

Base64URL (안전):
<https://api.example.com/verify?token=eyJ...fQ>

3.2 JWT 라이브러리 활용

주요 Java JWT 라이브러리

라이브러리특징GitHub Stars
jjwt가장 인기, Spring 친화적⭐ 9.5k

jjwt 사용 예시

import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.SignatureAlgorithm;
import io.jsonwebtoken.Claims;

public class JwtExample {

    private static final String SECRET_KEY = "mySecretKeyMinimum256BitsRequired123456789012345678901234";

    // JWT 생성
    public static String createJwt() {
        return Jwts.builder()
            // Header (자동 설정)
            .setHeaderParam("typ", "JWT")

            // Payload
            .setSubject("user@example.com")
            .claim("user_id", 1)
            .claim("name", "홍길동")
            .claim("role", "USER")
            .setIssuedAt(new Date())
            .setExpiration(new Date(System.currentTimeMillis() + 3600000)) // 1시간

            // Signature
            .signWith(SignatureAlgorithm.HS256, SECRET_KEY)

            .compact();
    }

    // JWT 파싱
    public static Claims parseJwt(String jwt) {
        return Jwts.parser()
            .setSigningKey(SECRET_KEY)
            .parseClaimsJws(jwt)
            .getBody();
    }

    // 사용 예시
    public static void main(String[] args) {
        // 생성
        String jwt = createJwt();
        System.out.println("JWT: " + jwt);

        // 파싱
        Claims claims = parseJwt(jwt);
        System.out.println("Subject: " + claims.getSubject());
        System.out.println("User ID: " + claims.get("user_id"));
        System.out.println("Name: " + claims.get("name"));
        System.out.println("Role: " + claims.get("role"));
    }
}

4. JWT 서명과 검증

4.1 대칭키(HMAC) 서명

HMAC (Hash-based Message Authentication Code)

같은 키로 서명하고 검증하는 방식

동작 원리

[서버]
 ├─ Secret Key: "mySecretKey123"
 ├─ JWT 생성 시: HMAC(header.payload, secretKey) → 서명
 └─ JWT 검증 시: HMAC(header.payload, secretKey) → 기대 서명
                 기대 서명 == 실제 서명 ? 유효 : 무효

코드 예시

import io.jsonwebtoken.SignatureAlgorithm;

public class HmacJwtExample {

    // ⚠️ 실무에서는 환경 변수나 설정 파일에서 로드
    private static final String SECRET_KEY = "mySecretKey256BitsMinimum12345678901234567890";

    // JWT 생성
    public String generateToken(User user) {
        return Jwts.builder()
            .setSubject(user.getEmail())
            .claim("user_id", user.getId())
            .setIssuedAt(new Date())
            .setExpiration(new Date(System.currentTimeMillis() + 3600000))

            // HMAC-SHA256 서명
            .signWith(SignatureAlgorithm.HS256, SECRET_KEY)

            .compact();
    }

    // JWT 검증
    public Claims validateToken(String token) {
        try {
            return Jwts.parser()
                .setSigningKey(SECRET_KEY)  // 같은 키로 검증
                .parseClaimsJws(token)
                .getBody();
        } catch (JwtException e) {
            throw new InvalidTokenException("유효하지 않은 토큰입니다.");
        }
    }
}

장점

  • ✅ 간단한 구현
  • ✅ 빠른 성능
  • ✅ 단일 서버나 신뢰할 수 있는 서버 간 통신에 적합

단점

  • ❌ Secret Key 공유 필요
  • ❌ Secret Key 노출 시 모든 토큰 위험
  • ❌ 여러 서비스가 Secret Key를 공유해야 함

4.2 비대칭키(RSA) 서명

RSA (Rivest-Shamir-Adleman)

개인키로 서명하고 공개키로 검증하는 방식

동작 원리

[인증 서버]                    [API 서버들]
  개인키 보관                    공개키만 보관
      ↓                              ↓
  JWT 생성 시:              JWT 검증 시:
  RSA(payload, 개인키)      RSA_verify(payload, 공개키)
      ↓                              ↓
   서명 생성                      서명 검증

키 생성

# 개인키 생성
openssl genrsa -out private_key.pem 2048

# 공개키 추출
openssl rsa -in private_key.pem -pubout -out public_key.pem

코드 예시

import io.jsonwebtoken.SignatureAlgorithm;
import java.security.*;
import java.security.spec.*;

public class RsaJwtExample {

    private PrivateKey privateKey;
    private PublicKey publicKey;

    public RsaJwtExample() throws Exception {
        // 키 쌍 생성 (실무에서는 파일에서 로드)
        KeyPairGenerator keyGen = KeyPairGenerator.getInstance("RSA");
        keyGen.initialize(2048);
        KeyPair keyPair = keyGen.generateKeyPair();

        this.privateKey = keyPair.getPrivate();
        this.publicKey = keyPair.getPublic();
    }

    // JWT 생성 (개인키로 서명)
    public String generateToken(User user) {
        return Jwts.builder()
            .setSubject(user.getEmail())
            .claim("user_id", user.getId())
            .setIssuedAt(new Date())
            .setExpiration(new Date(System.currentTimeMillis() + 3600000))

            // RSA 개인키로 서명
            .signWith(SignatureAlgorithm.RS256, privateKey)

            .compact();
    }

    // JWT 검증 (공개키로 검증)
    public Claims validateToken(String token) {
        return Jwts.parser()
            .setSigningKey(publicKey)  // 공개키로 검증
            .parseClaimsJws(token)
            .getBody();
    }
}

장점

  • ✅ 개인키는 인증 서버만 보관
  • ✅ 공개키는 여러 서비스에 배포 가능
  • ✅ 개인키 노출 없이 검증 가능
  • ✅ 마이크로서비스에 적합

단점

  • ❌ HMAC보다 느림
  • ❌ 키 관리 복잡
  • ❌ 구현이 복잡

4.3 서명 검증 과정

검증 단계

1. JWT 형식 확인
   ├─ 3개 부분으로 나뉘는가? (header.payload.signature)
   └─ Base64URL 형식인가?

2. Header 파싱
   ├─ alg 필드 확인
   └─ 지원하는 알고리즘인가?

3. 서명 검증
   ├─ Header와 Payload로 예상 서명 생성
   ├─ 실제 서명과 비교
   └─ 일치하면 통과, 불일치하면 거부

4. Claims 검증
   ├─ exp: 만료되지 않았는가?
   ├─ nbf: 유효 시작 시간이 되었는가?
   ├─ iss: 발급자가 올바른가?
   └─ aud: 의도된 대상인가?

Java 코드로 이해하기

public Claims validateToken(String token) {
    try {
        Claims claims = Jwts.parser()
            .setSigningKey(secretKey)

            // 자동 검증
            .parseClaimsJws(token)  // 서명 + 만료 시간 자동 검증
            .getBody();

        // 추가 검증 (필요시)
        String issuer = claims.getIssuer();
        if (!"<https://auth.example.com>".equals(issuer)) {
            throw new InvalidTokenException("잘못된 발급자");
        }

        return claims;

    } catch (ExpiredJwtException e) {
        throw new TokenExpiredException("토큰이 만료되었습니다.");
    } catch (UnsupportedJwtException e) {
        throw new InvalidTokenException("지원하지 않는 토큰입니다.");
    } catch (MalformedJwtException e) {
        throw new InvalidTokenException("잘못된 토큰 형식입니다.");
    } catch (SignatureException e) {
        throw new InvalidTokenException("서명 검증에 실패했습니다.");
    } catch (IllegalArgumentException e) {
        throw new InvalidTokenException("토큰이 비어있습니다.");
    }
}

4.4 서명 알고리즘 선택 기준

선택 가이드

상황별 알고리즘 선택

단일 서버 또는 신뢰할 수 있는 서버 간:
└─> HS256 (HMAC-SHA256)
    ├─ 간단한 구현
    ├─ 빠른 성능
    └─ Secret Key 공유 가능

마이크로서비스 또는 공개 API:
└─> RS256 (RSA-SHA256)
    ├─ 공개키 배포 가능
    ├─ 개인키는 인증 서버만 보관
    └─ 높은 보안성

모바일/IoT (리소스 제한):
└─> ES256 (ECDSA-SHA256)
    ├─ RSA보다 작은 키
    ├─ RSA보다 빠른 성능
    └─ 적은 대역폭 사용

비교표

알고리즘키 크기서명 속도검증 속도사용 사례
HS256256 bit⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐단일 서버, 내부 API
RS2562048 bit⭐⭐⭐⭐⭐⭐마이크로서비스, 공개 API
ES256256 bit⭐⭐⭐⭐⭐⭐⭐⭐모바일, IoT

📝 핵심 요약

JWT 구조

  • Header: 알고리즘과 토큰 타입 ({"alg":"HS256","typ":"JWT"})
  • Payload: 사용자 정보와 메타데이터 (Claims)
  • Signature: 무결성 검증을 위한 서명

Claims 종류

  • 등록된 클레임: iss, sub, aud, exp, iat 등
  • 공개 클레임: URL 형식의 클레임
  • 비공개 클레임: 개발자 정의 커스텀 클레임

서명 방식

  • HMAC (HS256): 대칭키, 간단하고 빠름, 단일 서버에 적합
  • RSA (RS256): 비대칭키, 마이크로서비스에 적합

보안 원칙

  • ❌ Payload에 민감한 정보 포함하지 않기 (암호화 X, 인코딩만 됨)
  • ✅ HTTPS 사용 필수
  • ✅ 짧은 만료 시간 설정
  • ✅ Secret Key 안전하게 보관

❓ 확인 질문

  2. Base64URL 인코딩과 암호화의 차이는 무엇인가요?
  3. HMAC 방식과 RSA 방식의 차이점은 무엇인가요?
  4. 왜 JWT의 Payload에 민감한 정보를 포함하면 안 되나요?
