1. 세션 기반 인증 복습과 한계점

1.1 세션 기반 인증 동작 방식 복습

이전 수업에서 배운 세션 기반 인증 방식을 복습해봅시다.

세션 인증 흐름

[클라이언트]                       [서버]                    [세션 저장소]

1. 로그인 요청
   POST /api/login
   { email, password }
   |------------------------->
                              2. 인증 확인
                              3. 세션 생성
                                 session_id: "abc123"
                                 user_id: 1
                                 |------------------>  [저장]
                              4. Set-Cookie 응답     session_id: abc123
   <-------------------------|    SESSION=abc123      user_id: 1

2. 브라우저에 쿠키 저장
   Cookie: SESSION=abc123

3. 이후 요청
   GET /api/profile
   Cookie: SESSION=abc123
   |------------------------->
                              7. 세션 조회
                                 |------------------>  [조회]
                                 <------------------|  user_id: 1
                              8. 사용자 식별
                              9. 응답
   <-------------------------|

세션 기반 인증의 특징

  • Stateful: 서버가 세션 정보를 저장하고 관리
  • 쿠키 기반: 세션 ID를 쿠키로 클라이언트에 전달
  • 서버 의존성: 세션 저장소(메모리, Redis 등) 필요

1.2 서버 측 세션 저장소의 확장성 문제

단일 서버 환경

[클라이언트]  →  [서버]
                  ↓
              [메모리/세션 저장소]
              session_id: abc123
              user_id: 1

단일 서버에서는 문제가 없습니다.

다중 서버 환경의 문제

[로드 밸런서]
      ↓
   ┌──┴──┐
   ↓     ↓
[서버1] [서버2]
  ↓       ↓
[세션]  [세션]
abc123   (없음)

문제 발생!
1. 사용자가 서버1에 로그인 → 서버1에 세션 생성
2. 다음 요청이 서버2로 라우팅
3. 서버2에는 세션 정보가 없음
4. 인증 실패! 😢

1.3 분산 환경에서의 세션 관리 문제

해결책 1: Sticky Session (세션 고정)

[로드 밸런서]
  - 같은 사용자는 항상 같은 서버로 라우팅
      ↓
   ┌──┴──┐
   ↓     ↓
[서버1] [서버2]

문제점:

  • 서버1에 장애 발생 시 해당 서버의 모든 세션 손실
  • 로드 밸런싱 효율 저하
  • 특정 서버에 부하 집중 가능

해결책 2: 세션 클러스터링 (Redis 등)

[서버1] [서버2] [서버3]
   ↓       ↓       ↓
      [Redis]
   세션 공유 저장소

코드 예시: Redis 세션 설정

// build.gradle
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-redis'
    implementation 'org.springframework.session:spring-session-data-redis'
}

// application.yml
spring:
  session:
    store-type: redis
  redis:
    host: localhost
    port: 6379

문제점:

  • Redis 같은 추가 인프라 필요
  • Redis 장애 시 모든 인증 불가
  • 네트워크 통신으로 인한 지연
  • 추가 비용 발생

1.4 세션 방식의 실무 한계 정리

확장성 문제

서버 10대 → 100대로 확장
- 세션 동기화 복잡도 증가
- Redis 부하 증가
- 네트워크 트래픽 증가

성능 문제

모든 API 요청마다:
1. Redis 조회 (네트워크 I/O)
2. 세션 데이터 역직렬화
3. 사용자 정보 추출

→ 응답 시간 증가

운영 복잡도

- Redis 클러스터 관리
- 세션 만료 정책 관리
- 백업 및 복구 전략
- 모니터링 및 알림

2. 토큰 기반 인증의 개념과 특징

2.1 Stateless 아키텍처의 이해

Stateless란?

서버가 클라이언트의 상태를 저장하지 않는 아키텍처

실생활 비유

Stateful (세션 방식)

영화관 직원이 관객의 티켓을 보관
관객: "제 좌석이 어디죠?"
직원: "제가 보관한 티켓을 확인해드릴게요" (저장소 조회)

Stateless (토큰 방식) 들어왔다면 권한이 있다는 뜻이다 -> 토큰이 있다면 인증되었다는 걸 확인 안 함

관객이 직접 티켓을 소지
관객: "제 좌석이 어디죠?" (티켓 제시)
직원: "티켓을 보니 A열 5번이네요" (티켓만 확인)

Stateless 아키텍처의 장점

[클라이언트]                    [서버1] [서버2] [서버3]
   토큰 보관                     상태 저장 X
      ↓                              ↓
모든 정보가 토큰에 포함    →    어느 서버든 토큰만 검증

JWT 토큰을 이용하기 때문에 모바일에도 친화적이다

코드로 이해하기

// Stateful (세션 방식)
@GetMapping("/api/profile")
public UserProfile getProfile(@CookieValue("SESSION") String sessionId) {
    // 1. 세션 저장소에서 조회 (외부 의존성)
    Session session = sessionRepository.findById(sessionId);

    // 2. 세션에서 사용자 정보 추출
    Long userId = session.getUserId();

    // 3. 사용자 조회
    User user = userRepository.findById(userId);

    return new UserProfile(user);
}

// Stateless (토큰 방식)
@GetMapping("/api/profile")
public UserProfile getProfile(@RequestHeader("Authorization") String authHeader) {
    // 1. 토큰에서 직접 정보 추출 (외부 의존성 없음)
    String token = authHeader.substring(7); // "Bearer " 제거
    Claims claims = jwtUtil.parseToken(token);

    Long userId = claims.get("user_id", Long.class);
    String email = claims.getSubject();

    // 2. 필요시에만 DB 조회 (토큰에 포함된 정보로 충분한 경우 생략 가능)
    User user = userRepository.findById(userId);

    return new UserProfile(user);
}

2.2 토큰의 자체 포함성 (Self-contained)

Self-contained란?

토큰 자체에 필요한 모든 정보가 포함되어 있음

토큰 구조 예시

{
  "user_id": 1,
  "email": "user@example.com",
  "role": "USER",
  "name": "홍길동",
  "exp": 1670000000,
  "iat": 1669996400
}

장점

  1. 데이터베이스 조회 감소
// 토큰에서 직접 정보 추출
Long userId = jwtUtil.getUserId(token);
String email = jwtUtil.getEmail(token);
String role = jwtUtil.getRole(token);

// DB 조회 없이 인가 가능!
if ("ADMIN".equals(role)) {
    // 관리자 권한 작업 수행
}
  1. 서버 간 독립성
[API 서버1]  [API 서버2]  [API 서버3]
    ↓            ↓            ↓
  토큰 검증   토큰 검증   토큰 검증
  (독립적)    (독립적)    (독립적)

  공유 저장소 불필요!
  1. 마이크로서비스 친화적
[인증 서비스] → 토큰 발급
               ↓
          [토큰]
         ↙  ↓  ↘
   [주문]  [결제]  [배송]
   서비스  서비스  서비스

   각 서비스가 독립적으로 토큰 검증

2.3 서버 부하 분산과 확장성 향상

세션 방식 vs 토큰 방식 비교

세션 방식: 수평 확장의 어려움

서버 추가 시마다 고려사항:
1. Redis 클러스터 구성
2. 세션 동기화 설정
3. 네트워크 설정
4. 모니터링 설정

[로드 밸런서]
      ↓
  [서버 10대]
      ↓
   [Redis 클러스터]
   (병목 지점)

토큰 방식: 수평 확장의 용이함

서버 추가 시:
1. 서버 추가
2. 끝!

[로드 밸런서]
      ↓
  [서버 100대]

  추가 인프라 불필요
  각 서버가 독립적으로 동작

부하 분산 시나리오

// 세션 방식
@GetMapping("/api/orders")
public List<Order> getOrders(@CookieValue("SESSION") String sessionId) {
    // 1. Redis 조회 (네트워크 I/O)
    Session session = redisTemplate.opsForValue().get(sessionId);

    // Redis가 병목!
    // 모든 서버가 Redis에 의존
}

// 토큰 방식
@GetMapping("/api/orders")
public List<Order> getOrders(@RequestHeader("Authorization") String token) {
    // 1. 토큰 검증 (CPU 연산만)
    Claims claims = jwtUtil.parseToken(token);

    // 네트워크 I/O 없음!
    // 각 서버가 독립적으로 처리
}

성능 비교

메트릭세션 방식토큰 방식
응답 시간100ms (Redis 조회 포함)50ms (로컬 검증만)
처리량1,000 req/sec5,000 req/sec
확장 비용선형 증가 (Redis 업그레이드 필요)일정 (서버만 추가)

2.4 토큰 기반 인증의 트레이드오프

근데 얘가 만능은 아님 티켓을 잃어버리면 영화를 못 보잖아

장점 ✅ 수평 확장 용이 ✅ 서버 부하 감소 (세션 저장소 불필요) ✅ 마이크로서비스에 적합 ✅ 모바일 앱 친화적

단점 ❌ 토큰 크기가 큼 (모든 요청에 포함) ❌ 토큰 만료 전 강제 무효화 어려움 ❌ 토큰에 민감한 정보 포함 불가 ❌ 토큰 탈취 시 대응 어려움

비교표

항목세션 방식토큰 방식
확장성⭐⭐⭐⭐⭐⭐⭐
보안⭐⭐⭐⭐⭐⭐⭐
성능⭐⭐⭐⭐⭐⭐⭐
구현 복잡도⭐⭐⭐⭐⭐⭐⭐
즉시 로그아웃⭐⭐⭐⭐⭐⭐⭐ 토큰 만료 전까지는 쩔수없

두 장점을 모두 취하기 위해 하이브리드 방식도 많이 사용한다

3. 토큰 기반 인증이 적합한 상황

3.1 RESTful API 설계

REST 원칙과의 일치

REST의 핵심 원칙 중 하나: Stateless

각 요청은 독립적이며, 서버는 클라이언트 상태를 저장하지 않음

RESTful API 원칙
├── Stateless: 서버가 클라이언트 상태 저장 안 함 ✅
├── Uniform Interface: 일관된 인터페이스
├── Client-Server: 명확한 역할 분리
└── Cacheable: 응답 캐싱 가능

예시: RESTful API with JWT

@RestController
@RequestMapping("/api/v1")
public class ProductController {

    // 토큰으로 사용자 식별 (Stateless)
    @GetMapping("/products")
    public ResponseEntity<List<Product>> getProducts(
        @RequestHeader("Authorization") String token
    ) {
        // 토큰에서 사용자 정보 추출
        Claims claims = jwtUtil.parseToken(token);

        // 각 요청이 독립적
        // 서버는 아무것도 저장하지 않음
        return ResponseEntity.ok(productService.findAll());
    }
}

3.2 마이크로서비스 아키텍처

마이크로서비스에서의 인증 문제

[인증 서비스]
     ↓
[API Gateway]
     ↓
  ┌──┴──┬──────┬──────┐
  ↓     ↓      ↓      ↓
[주문] [상품] [결제] [배송]

문제: 각 서비스가 사용자를 어떻게 인증할까?

세션 방식의 한계

❌ 모든 마이크로서비스가 Redis에 의존
   └─> 단일 장애점(Single Point of Failure)

❌ 서비스 간 네트워크 통신 증가
   └─> 지연 시간 증가

❌ Redis 확장 시 모든 서비스에 영향
   └─> 운영 복잡도 증가

토큰 방식의 장점

✅ 각 서비스가 독립적으로 토큰 검증

[인증 서비스]
   ↓ (토큰 발급)
[토큰: JWT]
   ↓
[API Gateway]
   ↓ (토큰 전달)
  ┌──┴──┬──────┬──────┐
  ↓     ↓      ↓      ↓
[주문] [상품] [결제] [배송]
  ↓     ↓      ↓      ↓
각각 독립적으로 토큰 검증 (공유 저장소 불필요)

코드 예시: 마이크로서비스에서 JWT 검증

// 주문 서비스
@RestController
@RequestMapping("/orders")
public class OrderController {

    @GetMapping("/my-orders")
    public List<Order> getMyOrders(@RequestHeader("Authorization") String token) {
        // 1. 토큰 검증 (독립적)
        Long userId = jwtUtil.getUserId(token);

        // 2. 주문 조회
        return orderService.findByUserId(userId);
    }
}

// 상품 서비스
@RestController
@RequestMapping("/products")
public class ProductController {

    @PostMapping("/{id}/reviews")
    public Review createReview(
        @PathVariable Long id,
        @RequestHeader("Authorization") String token,
        @RequestBody ReviewRequest request
    ) {
        // 1. 토큰 검증 (독립적)
        Long userId = jwtUtil.getUserId(token);

        // 2. 리뷰 생성
        return reviewService.create(id, userId, request);
    }
}

공통 JWT 라이브러리 공유

// shared-jwt-library (공통 라이브러리)
@Component
public class JwtUtil {

    @Value("${jwt.secret}")
    private String secretKey;

    public Claims parseToken(String token) {
        return Jwts.parser()
            .setSigningKey(secretKey)
            .parseClaimsJws(token)
            .getBody();
    }

    public Long getUserId(String token) {
        return parseToken(token).get("user_id", Long.class);
    }
}

3.3 SPA(Single Page Application) 클라이언트

SPA의 특징

전통적인 웹 앱:
페이지 이동마다 서버 요청
└─> 쿠키 자동 전송 (브라우저 기본 기능)

SPA (React, Vue, Angular):
한 번 로드 후 JavaScript로 동작
└─> API 호출 (fetch, axios)
└─> 쿠키를 사용할 수도 있지만, 토큰이 더 명시적

SPA에서 토큰 사용

// React 예시
import axios from 'axios';

// 1. 로그인 시 토큰 저장
const login = async (email, password) => {
  const response = await axios.post('/api/login', { email, password });
  const { token } = response.data;

  // LocalStorage에 토큰 저장
  localStorage.setItem('token', token);
};

// 2. API 요청 시 토큰 포함
const fetchProfile = async () => {
  const token = localStorage.getItem('token');

  const response = await axios.get('/api/profile', {
    headers: {
      'Authorization': `Bearer ${token}`
    }
  });

  return response.data;
};

// 3. Axios 인터셉터로 자동화
axios.interceptors.request.use(config => {
  const token = localStorage.getItem('token');
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});

장점

  1. 명시적 제어
// 개발자가 토큰을 직접 관리
// 언제 어디에 저장할지 결정 가능
localStorage.setItem('token', token);  // 영구 저장
// 또는
sessionStorage.setItem('token', token); // 탭 닫으면 삭제
  1. CORS 문제 해결
// 쿠키는 도메인 제약이 있지만
// Authorization 헤더는 자유롭게 전송 가능

// 프론트엔드: <https://www.example.com>
// API 서버: <https://api.example.com>

fetch('<https://api.example.com/users>', {
  headers: {
    'Authorization': `Bearer ${token}` // CORS 설정만 되면 OK
  }
});

3.4 모바일 애플리케이션 지원

모바일에서 쿠키의 한계

웹 브라우저:
- 쿠키 자동 관리 ✅
- Set-Cookie 헤더 자동 처리 ✅

모바일 앱 (Android, iOS):
- 쿠키 관리가 복잡 ❌
- 플랫폼마다 다른 쿠키 처리 방식 ❌
- WebView와 네이티브 코드 간 쿠키 공유 어려움 ❌

모바일에서 토큰 사용

// Android 예시 (Kotlin)
class AuthRepository {

    // 1. 로그인 후 토큰 저장
    suspend fun login(email: String, password: String): Result<User> {
        val response = apiService.login(LoginRequest(email, password))

        // SharedPreferences에 토큰 저장
        sharedPreferences.edit()
            .putString("access_token", response.accessToken)
            .apply()

        return Result.success(response.user)
    }

    // 2. API 요청 시 토큰 포함
    suspend fun getProfile(): Result<User> {
        val token = sharedPreferences.getString("access_token", null)

        return try {
            val response = apiService.getProfile("Bearer $token")
            Result.success(response)
        } catch (e: Exception) {
            Result.failure(e)
        }
    }
}

// 3. OkHttp 인터셉터로 자동화
class AuthInterceptor : Interceptor {
    override fun intercept(chain: Interceptor.Chain): Response {
        val token = sharedPreferences.getString("access_token", null)

        val request = chain.request().newBuilder()
            .addHeader("Authorization", "Bearer $token")
            .build()

        return chain.proceed(request)
    }
}

// iOS 예시 (Swift)
class AuthService {

    // 1. 로그인 후 토큰 저장
    func login(email: String, password: String) async throws -> User {
        let request = LoginRequest(email: email, password: password)
        let response = try await apiService.login(request)

        // Keychain에 토큰 저장 (안전)
        KeychainManager.shared.save(response.accessToken, forKey: "access_token")

        return response.user
    }

    // 2. API 요청 시 토큰 포함
    func getProfile() async throws -> User {
        guard let token = KeychainManager.shared.get("access_token") else {
            throw AuthError.notAuthenticated
        }

        var request = URLRequest(url: URL(string: "/api/profile")!)
        request.addValue("Bearer \\\\(token)", forHTTPHeaderField: "Authorization")

        let (data, _) = try await URLSession.shared.data(for: request)
        return try JSONDecoder().decode(User.self, from: data)
    }
}

4. 실무 의사결정 가이드

4.1 언제 세션을 사용할까?

세션이 적합한 경우

  1. 전통적인 서버 사이드 렌더링 애플리케이션
- Spring MVC + Thymeleaf
- JSP/Servlet
- PHP, Ruby on Rails
→ 브라우저 쿠키 자동 관리 활용
  1. 단일 서버 또는 소규모 서비스
- 트래픽이 적음
- 서버 확장 계획이 없음
→ 복잡한 토큰 관리 불필요
  1. 즉시 로그아웃이 필수인 경우
- 관리자 시스템
- 금융 서비스
→ 세션 삭제로 즉시 무효화 가능

4.2 언제 토큰을 사용할까?

토큰이 적합한 경우

  1. RESTful API 서버
- Stateless 설계
- 여러 클라이언트 지원 (웹, 모바일, IoT)
  1. 마이크로서비스 아키텍처
- 서비스 간 독립성
- 공유 저장소 부담 없음
  1. 대규모 트래픽
- 수평 확장 필요
- 서버 부하 분산
  1. 모바일 앱 + 웹 동시 지원
- 일관된 인증 방식
- 플랫폼 독립적

4.3 하이브리드 방식

세션 + 토큰 혼합 사용

// 웹 브라우저: 세션 사용
@GetMapping("/web/profile")
public String getProfile(HttpSession session, Model model) {
    User user = (User) session.getAttribute("user");
    model.addAttribute("user", user);
    return "profile";
}

// 모바일 API: 토큰 사용
@GetMapping("/api/profile")
public ResponseEntity<User> getProfileApi(
    @RequestHeader("Authorization") String token
) {
    User user = jwtUtil.getUserFromToken(token);
    return ResponseEntity.ok(user);
}

📝 핵심 요약

세션 방식의 한계

  • ❌ 서버 확장 시 세션 동기화 문제
  • ❌ Redis 같은 추가 인프라 필요
  • ❌ 모든 서버가 세션 저장소에 의존 (병목)

토큰 방식의 장점

  • ✅ Stateless: 서버가 상태 저장 안 함
  • ✅ Self-contained: 토큰에 모든 정보 포함
  • ✅ 수평 확장 용이
  • ✅ 마이크로서비스, SPA, 모바일에 적합

토큰이 적합한 상황

  • RESTful API 설계
  • 마이크로서비스 아키텍처
  • SPA (React, Vue, Angular)
  • 모바일 애플리케이션
  • 대규모 트래픽, 서버 확장 계획

❓ 확인 질문

  1. Stateless 아키텍처란 무엇이며, 어떤 장점이 있나요?
  2. 세션 방식에서 서버를 여러 대로 확장할 때 어떤 문제가 발생하나요?
  3. 토큰 기반 인증이 마이크로서비스 아키텍처에 적합한 이유는 무엇인가요?
